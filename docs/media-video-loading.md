# Gallery video loading and playback

The clicked/current item and keyboard-focused item attach their video source immediately. Other videos attach their source once when an observer rooted at the gallery's actual scrollport reports them within one visible scrollport height above or below it. One `ResizeObserver` measures that height for the gallery; a size change replaces the admission observer with a new pixel margin. Percentage root margins are not used because their vertical values [resolve against root width](https://w3c.github.io/IntersectionObserver/#dom-intersectionobserver-rootmargin). The admission region is independent of the current item's index and the image `preloadCount` setting. Source attachment remains in place after scrolling away. An unadmitted video has no `src` and uses `preload="none"`; an admitted video uses `preload="metadata"`. Preload is only a browser hint, so request suppression depends on absent `src`.

A separate zero-margin observer on the same scrollport controls playback visibility. Entering the admission region alone cannot start or resume playback. Scroll-out pauses and temporarily mutes a playing video. The component keeps playback intent through automatic pause and source replacement, then requests at most one resume after the current source has metadata and the visibility observer confirms the video is back in view. A repeated fallback captures the mute preference from before temporary scroll-out muting. A deliberate pause through native or supported gallery keyboard controls cancels playback intent; a later user mute or volume change supersedes the older recovery snapshot. A blocked current keyboard play command clears its own recovery intent. An older rejection cannot cancel a newer command or another source; a source-reset abort preserves intent. Programmatic visibility mute does not become a saved user volume preference.

The gallery reserves the logical media width and height before the video is fetched. A same-item, HTTPS CDN image may be shown as a poster. Native controls stay visible during deferred loading and after metadata arrives. `data-media-loaded` means geometry metadata is ready, and `data-video-first-frame` means `loadeddata` or cached `readyState >= 2` established frame data. Metadata readiness triggers scroll correction once per media object. Neither state alone proves playback progression.

Playback begins with the preferred display URL. On a native decode or unsupported-source error, the gallery can try at most two other validated MP4 variants from the same `MediaInfo`, once each. Network, abort, stall, user pause, and blocked `play()` events do not switch sources. When a resource timing entry exposes 401 or 403 for the active request, playback does not switch. Cross-origin media timing often hides response status; the media element alone cannot distinguish a hidden HTTP denial from an unsupported-source error. Recovery does not issue a probe request. A playback switch changes only the local video element; current-item identity and single/ZIP download source remain the preferred source. A localized notice identifies the playback substitution.

The source, media object, mounted element, and scroll root are checked before delayed load/error or observer events can publish state. A new media object resets attempts and readiness; a reorder of the same object retains its source and admission. On close, observer subscriptions and pending resume intent are disposed with the gallery element. Retired observer callbacks cannot admit media into a later session.

Volume persistence retires with the player. Closing flushes its last pending live preference; later volume events from a disposed hook or a replaced video cannot enqueue another settings save.

The event distinction and advisory preload behavior follow the [MDN video element reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video). The first-frame test follows [MDN's `loadeddata` definition](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/loadeddata_event); readiness additionally checks `readyState` for cached frames.
