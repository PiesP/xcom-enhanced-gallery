# Final Firefox ZIP validation

The release workflow packages `release-bundle/release/xcom-enhanced-gallery-firefox.zip`, then runs `vp run release:firefox-validate` on those exact bytes before uploading the bundle. The validator uses pinned `addons-linter` 10.15.0 with JSON output and inspects the ZIP's `content.js` with Acorn. The protected publication job checks the ZIP hash, source SHA, extension version, command, linter result, and warning disposition against the retained report before creating a release. The public release still contains exactly the established six assets.

The accepted warning is `UNSAFE_VAR_ASSIGNMENT` for `content.js`'s `innerHTML` assignment in Solid's `template()` factory. In the reviewed v2.3.10 ZIP (`e60ebc1f7582236ed760ab717ff35bb7aada5649e9dd6bac4e87dece75786239`), the assignment is at line 9791, column 4. The factory's `html` parameter reaches the `template` element sink, and every direct call supplies a string literal or a template literal without expressions. The structural check rejects aliasing, escaping references, dynamic inputs, additional `innerHTML`/`outerHTML` assignments, and calls to `insertAdjacentHTML`, `createContextualFragment`, `write` or `writeln`. A line number, factory name, or call count is never sufficient to accept the warning. This is a disposition for that compiler output shape, not a general proof that all HTML flows are safe.

The build artifact retains `release-bundle/validation/addons-linter.json` and `release-bundle/validation/firefox-final-zip.json`; the workflow also uploads these as a short-lived validation artifact when available. The latter records the command, linter version, ZIP hash, source SHA, extension version, static call count, and warning disposition. On a failed linter run, the raw JSON is retained when the linter emits it, and publication stops.

When Solid, the compiler, bundler, linter, or extension source changes, inspect the final ZIP and both reports. Errors and notices are rejected; only the exact reviewed warning is accepted. Review every new linter finding, the factory binding, its direct calls, and all HTML-writing paths. Update the narrow structural check and this disposition only after establishing the new data flow and adding negative coverage. Do not suppress the linter rule or accept a warning solely because its location resembles v2.3.10.

This local validation is separate from Mozilla Add-ons review, signing, and any live-site or installed-browser acceptance. Mozilla's [addons-linter](https://github.com/mozilla/addons-linter) documents the ZIP CLI and JSON report; its [extension security guidance](https://extensionworkshop.com/documentation/develop/build-a-secure-extension/) explains the broader trust boundary.
